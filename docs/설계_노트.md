# 설계 노트

과제 목표(B6-1-G1~G5)와 구두 평가 항목에 대한 답을 근거와 함께 정리한다.
"이렇게 하는 게 좋다"가 아니라 **이 저장소가 실제로 그렇게 되어 있는 지점**을 가리킨다.

---

## 1. 트래픽 흐름 — VPC / Subnet / Route Table / IGW 의 역할 (G1)

| 구성 요소 | 하는 일 | 없으면 |
| --- | --- | --- |
| **VPC** | 계정 안에 격리된 사설 네트워크 공간(`10.0.0.0/16`)을 만든다 | 인스턴스를 놓을 주소 공간 자체가 없다 |
| **Subnet** | VPC 를 가용영역(AZ) 단위로 쪼갠 구획(`10.0.1.0/24`). 인스턴스는 **서브넷 안에** 뜬다 | 인스턴스를 어느 AZ 에 놓을지 정할 수 없다 |
| **Internet Gateway** | VPC 와 인터넷을 잇는 **관문**. VPC 당 하나 붙인다 | VPC 는 바깥과 물리적으로 이어지지 않는다 |
| **Route Table** | "이 목적지로 가려면 어디로 보내라"는 **이정표**. 서브넷에 연결된다 | 관문이 있어도 패킷이 그리로 갈 길을 모른다 |

```text
Client ──▶ IGW ──▶ Route Table(0.0.0.0/0 → IGW) ──▶ Subnet ──▶ SG ──▶ EC2:80
```

### Public Subnet 을 "퍼블릭"으로 만드는 것은 이름이 아니다

서브넷 이름을 `public-subnet` 으로 지어도 아무 일도 일어나지 않는다.
퍼블릭이 되려면 **두 가지가 동시에** 필요하다.

1. 연결된 Route Table 에 `0.0.0.0/0 → IGW` 경로가 있을 것 → `01_network.sh` 의 `create-route`
2. 인스턴스에 퍼블릭 IP 가 붙을 것 → `modify-subnet-attribute --map-public-ip-on-launch`

기본 Route Table 에는 `10.0.0.0/16 → local` 하나뿐이다. 이건 **VPC 내부끼리만** 통하는 경로다.
그래서 아무것도 안 하면 그 서브넷은 사설 서브넷이다.

`map-public-ip-on-launch` 는 **이미 떠 있는 인스턴스에 소급 적용되지 않는다.**
켜기 전에 만든 인스턴스는 퍼블릭 IP 없이 그대로다 — 다시 만들어야 한다.

## 2. Security Group 과 IAM (G2)

| | Security Group | IAM |
| --- | --- | --- |
| 심사 대상 | **패킷** | **API 호출** |
| 질문 | "이 주소에서 이 포트로 들어와도 되나" | "이 주체가 이 리소스에 이 작업을 해도 되나" |
| 적용 지점 | ENI(인스턴스의 네트워크 인터페이스) | AWS 서비스 엔드포인트 |
| 상태 | **stateful** — 나간 요청의 응답은 규칙 없이 돌아온다 | 무상태. 매 호출마다 판정 |
| 어겼을 때 | 타임아웃 / 연결 거부 | `AccessDenied` / `UnauthorizedOperation` |

**서로를 대신하지 못한다.** SG 를 아무리 좁혀도 IAM 이 넓으면 콘솔에서 규칙을 바꿔 열어 버릴 수 있고,
IAM 이 좁아도 SG 가 열려 있으면 트래픽은 그대로 들어온다.

### 최소 권한을 왜 지키나 — 사고의 크기를 미리 정해 두는 것

키가 유출됐을 때 **무엇까지 당하는가**가 정책에 미리 적혀 있다.
`AdministratorAccess` 면 계정 전체고, 이 실습 정책이면 서울 리전의 EC2/VPC 까지다.
[`iam/README.md`](../iam/README.md) 가 무엇을 왜 뺐는지 항목별로 적어 두었다.
특히 `iam:AttachUserPolicy` 같은 **권한 상승 경로**를 뺀 것이 핵심이다 —
그게 있으면 다른 제한이 전부 무의미해진다.

### SSH(22)·DB 포트를 `0.0.0.0/0` 으로 열면 안 되는 이유

- 22 를 전체 공개하면 수 분 안에 자동화된 로그인 시도가 시작된다. 키 인증만 허용해도
  로그가 묻히고, 언젠가 설정 하나가 어긋나는 날 그게 문이 된다.
- DB 포트(3306/5432)는 더 나쁘다. 애초에 인터넷에서 닿을 이유가 없는 포트다.
- 대안: **소스 IP 제한**(이 실습), **SSM Session Manager**(포트를 아예 안 연다),
  **Bastion + 사설 서브넷**, **VPN**.

이 저장소는 주의로 지키지 않고 코드로 막는다 —
`02_security_group.sh` 는 `SSH_CIDR=0.0.0.0/0` 을 받으면 실행을 거부하고,
[`infra/check_sg.py`](../infra/check_sg.py) 가 규칙을 넣은 직후와 최종 검증에서 두 번 판정한다.

## 3. 가설 → 검증 순서를 지킨 이유 (G4)

외부 접속이 안 될 때 원인 후보는 최소 넷이다 — 라우팅 / 보안 그룹 / 퍼블릭 IP / 서버 프로세스.
**바깥에서 안쪽으로** 좁히면 각 단계가 다음 단계의 전제를 지워 준다.

```text
① 라우팅 → ② 보안 그룹 → ③ 퍼블릭 IP/DNS → ④ 서버 프로세스·로그
```

반대로 서버부터 보면 "nginx 는 살아 있다"까지 확인하고도 원인을 모르는 채 끝난다.
`04_verify.sh` 가 이 순서 그대로 검사하고, 요구사항 ID 마다 PASS/FAIL 을 찍는다.

**로그를 근거로 쓴다는 것**은 "확인했다"가 아니라 *무엇을 실행해 무엇이 나왔는지*를 남기는 것이다.
그래서 `04_verify.sh` 는 판정(`[PASS]`)만 찍지 않고 실제 값(`기본 경로: 0.0.0.0/0 → igw-...`)을
같이 찍는다. 나중에 이 출력만 봐도 그때 상태를 재구성할 수 있다.

## 4. 과금 요인과 정리 순서 (G5)

### 대표 과금 요인

| 요인 | 성격 | 이 실습에서 |
| --- | --- | --- |
| EC2 인스턴스 시간 | 켜져 있는 동안 계속 | t3.micro 1대 (프리티어) |
| **EBS 볼륨** | 인스턴스를 꺼도 **볼륨은 남아 과금** | `DeleteOnTermination=true` 로 같이 지운다 |
| **미연결 Elastic IP** | *연결되지 않은* 상태에서 시간당 과금 | **할당하지 않는다** |
| NAT Gateway | 시간당 + 데이터 처리량. 가장 흔한 "몰랐던 요금" | 만들지 않고, IAM 정책에도 권한이 없다 |
| ELB/ALB | 시간당 + LCU | 만들지 않는다 |
| 데이터 전송(아웃바운드) | GB 단위 | 실습 규모에서는 무시 가능 |

**EIP 가 특히 함정인 이유.** 붙어 있을 때는 무료인데 인스턴스를 지우면 "연결 해제" 상태가 되고,
**바로 그때부터 돈이 나간다.** 정리했다고 생각한 순간 과금이 시작되는 구조다.

### 삭제 순서는 왜 역순인가

AWS 리소스는 참조 관계가 있어서, 참조하는 쪽을 먼저 지우지 않으면 `DependencyViolation` 이 난다.

```text
인스턴스 종료 → (루트 EBS 자동 삭제) → EIP 해제 → SG 삭제
→ 라우팅 연결 해제 → 라우트 테이블 삭제 → IGW 분리·삭제 → 서브넷 삭제 → VPC 삭제
```

`99_cleanup.sh` 가 이 순서로 지우고, 마지막에 **태그로 다시 훑어** 잔여를 확인한다.
하나라도 남으면 종료 코드 1 로 끝난다. 삭제 명령이 성공했다는 것과
실제로 없어졌다는 것은 다른 이야기이기 때문이다.

### 추적 기준 — 태그

모든 `create-*` 호출에 `Project=codyssey-b6-1` 태그를 붙인다(`00_env.sh` 의 `tag_spec`).
정리 스크립트는 **이 태그만으로** 대상을 찾는다. 이름 규칙이나 기억에 의존하지 않으므로,
`.state` 파일을 잃어버려도 잔여 확인은 동작한다.

## 5. 구조 — 왜 스크립트를 이렇게 쪼갰나

```text
00_env.sh   설정·헬퍼          (나머지 전부가 source)
01 → 02 → 03                   순서대로 실행. 각자 자기 리소스만 만든다
04_verify.sh                   판정 전담. 아무것도 만들지 않는다
99_cleanup.sh                  삭제 전담
check_sg.py                    보안 그룹 판정 로직 (02 와 04 가 공유)
```

- **단계를 나눈 이유**: 중간에 실패하면 그 단계만 고쳐 다시 돌린다.
  `.state` 에 만든 ID 를 적어 두므로 **재실행해도 새로 만들지 않는다.**
- **검증을 분리한 이유**: 만든 스크립트가 스스로를 검사하면 같은 착각을 두 번 한다.
  `04_verify.sh` 는 `.state` 의 ID 만 받아 **AWS 에 직접 물어본다.**
- **`check_sg.py` 를 공유하는 이유**: 생성 직후 점검과 최종 검증이 다른 기준을 쓰면
  한쪽만 통과하는 상태가 생긴다. 판정 로직을 한 파일에만 둬서 그 틈을 없앴다.

## 6. 확장 — 인스턴스를 2대로 늘린다면

지금 구조에서 **병목은 인스턴스가 아니라 "퍼블릭 IP 하나"** 다.
클라이언트는 IP 를 직접 부르므로, 2대가 되는 순간 어디로 보낼지 정할 주체가 없다.

| 추가할 것 | 왜 |
| --- | --- |
| **ALB(Application Load Balancer)** | 단일 진입점. 클라이언트는 ALB DNS 만 안다. 헬스체크로 죽은 인스턴스를 자동 제외 |
| **Public Subnet 2개 (서로 다른 AZ)** | ALB 는 **최소 2개 AZ** 의 서브넷을 요구한다. AZ 하나가 죽어도 서비스가 산다 |
| **Security Group 분리** | ALB 용 SG(80 ← 0.0.0.0/0) 와 인스턴스용 SG(80 ← **ALB SG**). 인스턴스는 더 이상 인터넷에 직접 노출되지 않는다 |
| **Auto Scaling Group + Launch Template** | "2대"를 손으로 세지 않고 목표 대수로 관리. `user-data.sh` 가 그대로 Launch Template 이 된다 |
| **인스턴스를 Private Subnet 으로** | 그러면 아웃바운드용 NAT Gateway 가 필요하다 — **여기서 비용이 확 뛴다.** 실습 규모에서는 과한 선택 |

**설계에서 먼저 정해야 하는 것은 상태(state)다.** 지금은 정적 페이지라 어느 인스턴스가 받아도 같지만,
세션이나 업로드 파일이 생기면 인스턴스 로컬 디스크에 두면 안 된다(ElastiCache / S3 / RDS 로 분리).
로드밸런서를 붙이기 전에 이걸 정하지 않으면, 사용자가 새로고침할 때마다 로그아웃되는 서비스가 된다.

`/health` 를 미리 만들어 둔 것도 이 때문이다. ALB 의 헬스체크 대상이 그대로 준비돼 있다.

## 7. Billing 에 예상치 못한 비용이 찍혔다면

**의심 순서** — 비싼 것부터, 그리고 "안 지웠을 법한 것"부터.

1. **NAT Gateway** — 시간당 + 데이터 처리량. 실습에서 실수로 만들면 하루 만에 눈에 띈다
2. **미연결 Elastic IP** — 정리했다고 생각한 뒤부터 과금되는 구조
3. **EBS 볼륨 / 스냅샷** — 인스턴스를 지워도 남는다. `available` 상태 볼륨을 찾는다
4. **다른 리전의 리소스** — 콘솔은 리전마다 화면이 따로다. **보이지 않은 채 계속 돌아간다**
5. **ELB/ALB, RDS** — 만들었다면 시간당

**추적 방법**

```bash
# 1) 어떤 서비스에서 나왔는지 — Cost Explorer 를 서비스별로 본다
#    콘솔: Billing → Cost Explorer → Group by: Service

# 2) 리전별로 다시 쪼갠다 (Group by: Region) — 4번 후보가 여기서 드러난다

# 3) 태그로 좁힌다. 이 실습은 모든 리소스에 Project=codyssey-b6-1 을 달았다
aws --region ap-northeast-2 ec2 describe-instances \
  --filters "Name=tag:Project,Values=codyssey-b6-1" \
  --query 'Reservations[].Instances[].[InstanceId,State.Name]'

# 4) 태그가 없는(=추적 밖) 리소스를 찾는다 — 진짜 범인은 보통 여기 있다
aws --region ap-northeast-2 ec2 describe-volumes \
  --filters "Name=status,Values=available" --query 'Volumes[].[VolumeId,Size,CreateTime]'
```

**재발 방지**는 사람의 주의가 아니라 장치로 만든다.

- 생성 시점부터 태그를 단다 → 정리 스크립트가 이름 기억에 의존하지 않는다
- IAM 정책에 `aws:RequestedRegion` 조건 → 다른 리전 생성 자체가 거부된다
- 정책에 NAT Gateway / ELB / RDS 권한을 아예 넣지 않는다 → **실수로도 못 만든다**
- AWS Budgets 로 임계값 알림을 걸어 둔다 → 다음에 잊었을 때 사람이 아니라 시스템이 알려준다
