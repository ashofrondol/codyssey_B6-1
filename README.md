# 내가 만든 웹사이트를 인터넷에 올려 누구나 쓰게 하기

AWS 에서 **VPC 로 격리된 네트워크를 직접 설계**하고, Public Subnet 의 EC2 에 웹 서버를 올려
외부에서 접속 가능한 웹 서비스를 완성한다. 코디세이 B6-1 미션 산출물이다.

- **리전**: `ap-northeast-2` (서울) — 스크립트와 IAM 정책 양쪽에 고정돼 있다
- **구성**: VPC 1 / Public Subnet 1 / Internet Gateway 1 / EC2 1대(t3.micro, nginx)
- **접근 제어**: HTTP(80) 는 전체 공개, SSH(22) 는 **내 IP 에서만**
- **권한**: `AdministratorAccess` 없이, 실습에 필요한 액션만 나열한 IAM 정책 1개

#### 원문 — 1. 미션 소개

> "일단 서버에 올렸는데 외부에서 안 들어와요." 포트를 막아놓으셨습니까, 보안 그룹이 없는 겁니까. 클라우드는 그냥 빠른 컴퓨터가 아니라 네트워크, 보안, IAM이 묶인 환경입니다. 열린 포트 하나로 서버가 털리는 게 현실입니다. VPC로 격리된 네트워크를 직접 설계하고, 최소권한 원칙까지 적용한 서비스 환경을 완성합니다.
>
> 클라우드는 필요한 만큼의 컴퓨팅, 네트워크, 스토리지를 빠르게 구성해 서비스를 안정적으로 배포·운영하기 위한 기반 기술입니다. 웹 서비스 운영, 트래픽 증가 대응, 보안 경계 분리 같은 상황에서 활용됩니다.
>
> 이번 미션에서는 웹 서비스 인프라를 직접 구축하며 컴퓨팅, 네트워크, 스토리지, 보안 요소를 조합해 안정적인 서비스 환경을 설계 및 구현합니다. VPC로 격리된 네트워크를 구성하고, 가상 서버에 애플리케이션을 배포해 외부에서 접속 가능한 웹 서비스를 완성합니다.
>
> 또한 보안 그룹과 IAM 최소권한을 적용하고, 통신/권한 오류가 발생하면 로그를 근거로 원인을 분석해 해결합니다. 이를 통해 네트워크 흐름, 보안 원칙·문제 해결 과정을 결과물로 확인하며, 현업에서 활용 가능한 기초 클라우드 설계 및 운영 감각을 갖추게 됩니다.

#### 💡 (해설) 이 과제가 진짜로 묻는 것

> 💡 이 과제는 "AWS 콘솔에서 EC2 하나 띄우기"를 묻는 게 **아니다**. 묻는 것은 네 가지다.
>
> 1. **패킷 한 개가 인터넷에서 내 Nginx 프로세스까지 도달하기까지 거치는 모든 관문을 설명할 수 있는가.** IGW → Route Table → Subnet → Security Group → 퍼블릭 IP/ENI → 서버 프로세스. 이 사슬 중 하나만 끊겨도 "안 들어와요"가 된다. 그래서 과제는 아키텍처 다이어그램을 제출물 1번으로 요구한다.
> 2. **네트워크 경계(Security Group)와 API 권한 경계(IAM)를 구분할 수 있는가.** 둘 다 "보안"이지만 통제하는 대상이 완전히 다르다(패킷 vs. AWS API 호출). 이걸 섞어 이해하면 SG를 열어놓고 IAM을 조이는 식의 엉뚱한 조치를 하게 된다.
> 3. **고장을 추측이 아니라 가설-검증으로 다룰 수 있는가.** 제출물 3번(트러블슈팅 보고서)이 `증상 → 가설 → 검증 → 조치 → 결과 → 재발방지` 6단계를 못 박은 이유다. "이것저것 눌러보니 됐다"는 감점 대상이다.
> 4. **비용을 인프라의 속성으로 인식하는가.** 클라우드 리소스는 만들면 끝이 아니라 **끄기 전까지 과금**된다. 제출물 4번(정리 체크리스트)이 별도 산출물인 것은 "정리"가 예의가 아니라 요구사항이기 때문이다.

### 0.3 과제 목표 — 수료 후 스스로 설명할 수 있어야 하는 것

#### 원문 — 3. 과제 목표

> 이 과제를 마친 후, 학습자는 아래를 스스로 설명할 수 있어야 한다.

1. VPC, Subnet, Route Table, Internet Gateway가 각각 어떤 역할을 하며 **트래픽 흐름이 어떻게 이어지는지** 말로 설명할 수 있다.
2. **Security Group과 IAM의 역할 차이**를 구분할 수 있고, **최소 권한 원칙을 왜/어떻게 적용**하는지 설명할 수 있다.
3. 외부 요청이 EC2의 웹 서버까지 도달하기 위해 필요한 설정(**라우팅 / 퍼블릭 IP / 보안그룹**)을 논리적으로 설명할 수 있다.
4. 오류 발생 시 **로그/증상을 근거로 원인을 가설화**하고, 검증 후 조치하는 트러블슈팅 과정을 설명할 수 있다.
5. **클라우드 과금이 발생하는 대표 요인**을 알고, 실습 리소스를 **안전하게 정리하는 순서와 이유**를 설명할 수 있다.

> 💡 "설명할 수 있다"가 5개 모두의 서술어다. 즉 이 과제의 평가는 **동작하는 인프라 + 말로 설명되는 근거**의 쌍으로 이뤄진다. 콘솔에서 클릭해서 됐더라도 왜 됐는지 못 말하면 목표 미달이다. 평가 체크리스트가 "2. 구현 구조 설명", "3. 핵심 개념 이해", "4. 확장 사고" 세 절을 따로 두고 있는 이유가 이것이다.

### 0.4 기능 요구 사항 (필수)

#### 원문 — 4. 기능 요구 사항

> 다음 요구사항을 모두 만족해야 한다.

#### R1. 네트워크 구성

- [ ] **R1-1** VPC 1개를 생성한다.
- [ ] **R1-2** Public Subnet 1개를 생성한다.
- [ ] **R1-3** Internet Gateway를 VPC에 연결한다.
- [ ] **R1-4** Public Subnet의 Route Table에 `0.0.0.0/0` → Internet Gateway 경로가 존재해야 한다.
- [ ] **R1-5** Public Subnet에 배치된 인스턴스는 인터넷으로 **아웃바운드** 통신이 가능해야 한다. (예: `curl https://example.com` 성공)

> 💡 (해설) 원문 PDF에서는 이 명령이 `curl <https://example.com >` 로 추출되는데, 이는 PDF의 하이퍼링크 마크업이 텍스트로 새어나온 것이다. 실제 명령은 `curl https://example.com` 이다.

#### R2. 컴퓨트 및 웹 서버 배포

- [ ] **R2-1** Public Subnet에 EC2 인스턴스 **1대**를 생성한다.
- [ ] **R2-2** **SSH**로 인스턴스에 접속할 수 있어야 한다.
- [ ] **R2-3** 웹 서버(**Nginx 등**)를 설치하고 **실행 상태**여야 한다.
- [ ] **R2-4** 인스턴스에서 `curl http://localhost` 요청이 **200 응답**을 반환해야 한다.

> 💡 (해설) 원문 PDF의 `curl <http://localhost >` 역시 링크 마크업 잔재이며 실제 명령은 `curl http://localhost` 이다. R2-4는 "인스턴스 **내부**에서"의 검증이고, R5는 "**외부**에서"의 검증이다. 둘은 별개 요구사항이며 둘 다 통과해야 한다 — 내부 200 / 외부 실패라면 원인은 서버가 아니라 SG·라우팅·퍼블릭 IP 쪽이라는 신호다.

#### R3. 접근 제어(보안 그룹)

- [ ] **R3-1** Security Group 인바운드는 **원칙적으로 필요한 포트만** 허용한다.
- [ ] **R3-2** **HTTP(80)** 는 `0.0.0.0/0` 에서 접근 가능해야 한다.
- [ ] **R3-3** **SSH(22)** 는 **학습자 개인 IP(또는 지정된 IP 대역)에서만** 접근 가능해야 한다.
- [ ] **R3-4** `0.0.0.0/0` 에 대해 **전체 포트(0-65535) 허용 규칙은 생성하지 않는다.**

#### R4. 권한(IAM) 최소권한

- [ ] **R4-1** 실습에 사용하는 IAM 사용자(또는 Role) **1개**를 사용한다.
- [ ] **R4-2** 해당 IAM 권한은 **EC2/VPC/Security Group 구성에 필요한 범위**로 제한한다.
  - 예: 생성·조회·태그·연결 등 실습에 필요한 작업 중심
  - 예: 실습과 무관한 서비스(S3/RDS 등) 권한은 부여하지 않음
- [ ] **R4-3** 관리자 권한(**AdministratorAccess**)은 부여하지 않는다.

#### R5. 외부 접속 검증(택 1)

> 아래 방식 중 1개를 선택해 "외부에서 접속 가능"을 증명해야 한다.

- [ ] **R5-1** 다음 중 **1개**를 선택해 증명한다.
  - **(A)** 브라우저에서 `http://<퍼블릭IP>` 로 접속했을 때 페이지가 정상 표시된다.
  - **(B)** `GET http://<퍼블릭IP>/health` 호출이 **200을 반환하며 고정된 응답(예: "OK")** 을 확인할 수 있다.
- [ ] **R5-2** 선택한 방식(A/B)은 **`README.md` 에 명시한다.**

#### R6. 운영 안정성(과금 방지)

- [ ] **R6-1** 실습 종료 후, 생성한 리소스를 정리하고 체크리스트에 **"종료/삭제 완료" 근거를 남긴다.**
- [ ] **R6-2** 최소한 다음 항목은 정리 완료를 확인해야 한다: **EC2, EBS(볼륨), Elastic IP, Internet Gateway, VPC**

### 0.5 보너스 과제 (선택)

#### 원문 — 5. 보너스 과제 (선택)

#### B1. 보너스 1 – HTTPS 적용하기

#### B2. 보너스 2 – Docker 컨테이너로 웹 서비스 배포하기

- [ ] **B2** EC2 인스턴스 내부에 **Docker를 설치**하고, **컨테이너로 웹 서비스를 실행**한다.
  - 이미지 선택은 자유(이전 미션에서 만든 이미지 또는 공개 이미지 사용 가능)
- [ ] **B2-1** (필수) 인스턴스 **내부**에서 `curl http://localhost` 가 정상 응답(예: **200**)을 반환
- [ ] **B2-2** (필수) **외부**에서 `http://<퍼블릭IP>` 접속 또는 `GET /health` 호출 중 **1개**로 정상 응답 확인
- [ ] **B2-3** `README.md` 에 아래 내용을 포함한다.
  - 실행한 **컨테이너 이미지명과 실행 방식**
  - **포트 매핑 정보**
- [ ] **B2-4** **검증 결과 스크린샷 2장 이상**
  - `docker ps` (컨테이너 **Up** 상태)
  - 외부 접속 결과(브라우저 화면 또는 `/health` 호출 결과)

> 💡 (해설) B2의 "(필수)"는 **보너스 2를 선택했을 때의 필수**라는 뜻이다. 보너스 자체는 선택이다. 원문 PDF에서 첫 항목은 `필수)` 로, 둘째 항목은 `(필수)` 로 괄호가 어긋나 있는데 내용상 둘 다 동일한 "(필수)"이다. 또 `curl <http://localhost 가>` 역시 링크 마크업 잔재로, 실제는 `curl http://localhost` 가 정상 응답을 반환한다는 뜻이다.

> Amazon Web Service

#### 원문 — 7. 제약 사항

##### 비용/계정

- **프리 티어 범위 내**에서 진행한다.
- **루트 계정은 사용하지 않으며**, 별도로 생성한 **IAM 사용자/Role로만 콘솔에 접근**한다.
- 실습 종료 후 생성한 리소스는 **모두 종료/삭제**하여 과금이 발생하지 않도록 한다.

##### 리전

- 모든 리소스는 **서울 리전(`ap-northeast-2`)** 에 생성한다.

##### 실행 환경(권장, 최소 가이드)

| 항목 | 규격 |
| --- | --- |
| 인스턴스 | 프리티어 대상 micro 급 인스턴스 **1대** (예: `t2.micro` 또는 `t3.micro` 중 택 1) |
| OS | **Ubuntu LTS** 또는 **Amazon Linux** 계열 중 택1 |
| 스토리지(EBS) | **8~10GiB** 수준에서 시작(불필요한 증설 지양) |
| 키페어 | **1개** 생성 후 안전하게 보관(**재발급 불가 전제**) |

##### 보안

- 보안 그룹 인바운드는 **필요 포트만** 허용한다.
- **HTTP(80)** 는 `0.0.0.0/0` 에서 접근 가능해야 한다.
- **SSH(22)** 는 **학습자 개인 IP(또는 지정된 IP 대역)** 에서만 접근 가능해야 한다.
- `0.0.0.0/0` 에 대해 **전체 포트(0-65535) 허용 규칙은 생성하지 않는다.**
- 운영/관리 목적 포트(예: SSH)는 임시로 열었다가 잊는 사고가 잦으므로, **소스 제한(내 IP)** 을 유지한다.

##### 운영/정리(필수)

> 과금 방지를 위해 아래 리소스는 **생성 시점부터 "정리 대상"으로 추적**한다.

- **EC2**(종료 상태 확인)
- **Elastic IP**(Release 확인)
- **NAT Gateway**(삭제 확인, 생성했다면)
- **ELB/ALB**(삭제 확인, 생성했다면)
- **RDS**(삭제 확인, 생성했다면)
- **EBS Volumes**(미사용 볼륨 포함 삭제 확인)
- 모든 리소스 삭제 후 **Billing Dashboard 확인을 권장**한다.

### 0.8 📚 이 과제가 공부하길 원하는 것 (학습 지도)

> 💡 아래 표 전체가 (해설)이다. 왼쪽 두 칸은 원문 요구사항을, 오른쪽 두 칸은 그 요구가 겨냥하는 개념과 자기점검 질문을 담았다. "스스로 답해볼 질문"은 평가 체크리스트의 *핵심 개념 이해* / *확장 사고 및 트러블슈팅* 항목을 그대로 녹인 것이므로, 평가자가 실제로 물어볼 질문이라고 봐도 된다.

| 요구사항 | 표면적으로 시키는 일 | 실제로 학습시키려는 개념 | 스스로 답해볼 질문 |
| --- | --- | --- | --- |
| **R1-1, R1-2** | VPC 1개 + Public Subnet 1개 만들기 | **네트워크 격리와 주소 설계**. VPC는 내 계정 안의 논리적으로 격리된 사설 네트워크이고, Subnet은 그 CIDR을 쪼개 AZ에 묶는 단위다. "Public/Private"는 AWS가 부여하는 속성이 아니라 **라우팅 결과로 정해지는 성격**이다. | VPC의 CIDR을 `/16`으로 잡고 Subnet을 `/24`로 자르면 몇 개의 Subnet을 만들 수 있나? Subnet이 AZ에 묶이는 이유는? "Public Subnet"이라는 이름만으로는 아무것도 public이 되지 않는 이유는? |
| **R1-3, R1-4** | IGW 붙이고 Route Table에 `0.0.0.0/0 → IGW` 넣기 | **라우팅 테이블이 Subnet의 성격을 결정한다**. IGW를 VPC에 attach만 해도 트래픽은 흐르지 않는다. 해당 Subnet에 **연결된(associated)** Route Table의 기본 경로가 IGW를 가리켜야 비로소 Public Subnet이 된다. 또 IGW는 퍼블릭 IP ↔ 사설 IP의 1:1 NAT 역할도 수행한다. | Public Subnet Route Table의 기본 경로(`0.0.0.0/0 → IGW`)가 왜 필요한가? IGW를 attach했는데도 인터넷이 안 되면 무엇을 먼저 보겠는가? Route Table을 Subnet에 **연결(associate)** 하지 않으면 무슨 일이 벌어지나? |
| **R1-5** | `curl https://example.com` 성공 | **인바운드와 아웃바운드는 별개의 경로다**. SG는 stateful이라 아웃바운드 허용 → 응답 인바운드 자동 허용이지만, NACL은 stateless라 양방향을 따로 열어야 한다. 아웃바운드가 되려면 (a) 기본 경로 (b) 퍼블릭 IP 또는 NAT (c) DNS 해석이 모두 필요하다. | `curl https://example.com` 이 실패했을 때, DNS 문제인지 라우팅 문제인지 어떻게 1분 안에 구분하나? (`dig`/`curl -v`/`ip route`) Private Subnet이라면 무엇을 추가해야 하나? |
| **R2-1, R2-2** | EC2 1대 띄우고 SSH 접속 | **키 기반 인증과 접속 경로의 분리**. 키페어는 재발급 불가(원문 명시)이며 private key는 `chmod 400`이 요구된다. SSH 실패는 (1) SG 22 차단 (2) 키 권한/키 불일치 (3) 퍼블릭 IP 미할당 (4) 인스턴스 미기동 — 원인이 최소 4갈래다. | SSH가 **timeout**으로 실패하는 것과 **permission denied (publickey)** 로 실패하는 것은 각각 어느 계층의 문제인가? 키를 분실하면 그 인스턴스에 다시 들어갈 방법이 있나? |
| **R2-3, R2-4** | Nginx 설치 후 `curl http://localhost` 200 | **"서버가 떠 있다"의 세 가지 층위**를 분리하는 훈련: ① 프로세스 실행(`systemctl status`) ② 포트 리스닝(`ss -tlnp`, 0.0.0.0 vs 127.0.0.1) ③ 응답 코드. localhost 200은 ①②③이 정상이라는 뜻이고, 이후 외부 실패는 전부 **인스턴스 밖**의 문제로 범위가 좁혀진다. | 웹 서버가 `127.0.0.1:80` 에만 바인딩되어 있으면 localhost curl은 성공하는데 외부는 실패한다 — 어떻게 확인하나? `systemctl enable` 을 안 하면 재부팅 후 무슨 일이 생기나? |
| **R3-1, R3-2, R3-3** | 80은 전체 공개, 22는 내 IP만 | **최소 권한 원칙의 네트워크판**. 공개 서비스 포트와 운영 포트의 노출 면적은 달라야 한다. SSH를 `0.0.0.0/0` 에 열면 봇넷의 무차별 대입 표적이 되며, 이는 이론이 아니라 분 단위로 관측되는 현실이다. | SSH(22) 또는 DB 포트를 `0.0.0.0/0` 로 열면 안 되는 이유와 **대안**(SSM Session Manager, Bastion Host, VPN, 포트 노킹)은? 내 집 IP가 유동이라 매번 바뀐다면 어떻게 운영하나? |
| **R3-4** | 전체 포트(0-65535) 허용 규칙 금지 | **"일단 다 열고 나중에 좁히자"가 왜 실패하는가**. 임시 규칙은 잊히고, 잊힌 규칙이 사고가 된다. 원문이 제약 사항에서 굳이 한 번 더 반복한 항목이다. | SG를 다 열어두고 디버깅하면 **어떤 정보를 잃게 되는가**? (힌트: 막히는 지점이 드러나지 않아 원인 규명이 오히려 늦어진다) SG와 NACL 중 "명시적 거부(deny)"를 표현할 수 있는 건 어느 쪽인가? |
| **R4-1, R4-2, R4-3** | IAM 사용자 1개, 필요한 범위만, Admin 금지 | **SG와 IAM의 책임 범위 차이**. SG는 *패킷*이 인스턴스에 닿을지를 통제하고, IAM은 *AWS API 호출*(`ec2:RunInstances` 등)의 허용 여부를 통제한다. 둘은 서로를 대체하지 못한다. IAM에는 정책 평가 로직(명시적 Deny > Allow > 암묵적 Deny)이라는 별도 규칙이 있다. | Security Group과 IAM의 책임 범위 차이를 한 문장으로 말해보라. IAM 권한이 부족해 작업이 실패했다면 **권한을 무작정 올리지 않고** 어떻게 최소 범위를 찾아가나? (힌트: CloudTrail의 AccessDenied 이벤트 / 오류 메시지의 액션명 / IAM Access Analyzer) |
| **R4 전반 + 제약(루트 계정 금지)** | 루트 대신 IAM 사용자로만 콘솔 접근 | **계정 위계와 침해 반경(blast radius)**. 루트는 청구·계정 폐쇄까지 가능한 최상위 주체라 일상 작업에 쓰면 사고 시 복구 불가 영역까지 노출된다. MFA, 액세스 키 수명주기도 같은 맥락. | 루트 계정으로만 할 수 있는 작업은 무엇인가? 액세스 키가 GitHub에 유출되면 **순서대로** 무엇을 하나? |
| **R5-1, R5-2** | 외부에서 A 또는 B로 접속 증명 | **엔드투엔드 검증과 증거의 재현성**. (A)는 사람이 눈으로 보는 검증, (B)는 기계가 판정할 수 있는 검증(고정 응답 + 200)이다. B를 고르면 헬스체크 엔드포인트라는 운영 개념(로드밸런서·오토스케일링의 판정 근거)까지 들어온다. | A와 B 중 무엇을 골랐고, 그 선택을 위해 무엇을 어떻게 **구성**했는가? (B라면 `/health` 를 Nginx `location` 으로 만들었는가, 앱 라우트로 만들었는가?) 스크린샷 한 장이 "외부에서 접속됨"의 증거가 되려면 무엇이 찍혀 있어야 하나? |
| **R5 실패 시** | (검증이 안 될 때) | **고장 분리(fault isolation)의 순서**. 평가 체크리스트가 명시한 점검 순서: **라우팅 → SG → 퍼블릭 IP/DNS → 서버 프로세스/로그**. 안쪽에서 바깥으로(또는 바깥에서 안쪽으로) 일관된 방향으로 좁혀야 한다. | 외부 접속이 안 될 때 이 4단계를 각각 **어떤 명령/화면으로** 확인하나? `curl -v` 가 `Connection refused` 일 때와 `Connection timed out` 일 때 의심 지점이 어떻게 갈리는가? |

### 0.9 자주 놓치는 함정

1. **"IGW를 VPC에 연결(attach)"과 "Route Table에 경로 추가"는 서로 다른 두 개의 요구사항이다.** R1-3과 R1-4가 별도 항목인 이유다. IGW만 붙이고 기본 경로를 안 넣으면 인터넷은 여전히 안 된다. 거기에 더해 **Route Table을 해당 Subnet에 associate** 까지 해야 완성인데, 이 세 번째 단계는 원문에 명시되어 있지 않아 더 자주 빠진다.

2. **`curl http://localhost` 200(R2-4)과 외부 접속 200(R5-1)은 서로를 대체하지 않는다.** 내부만 통과해도 요구사항 미충족이고, 반대도 마찬가지다. 두 증거를 **각각** 남겨야 한다.

3. **HTTP(80)는 `0.0.0.0/0` 허용이 *요구사항*이고, SSH(22)의 `0.0.0.0/0` 허용은 *금지*다.** "모든 포트를 좁게"가 아니라 **포트별로 노출 범위가 다르다**. 공개 서비스 포트를 내 IP로만 열면 그것도 R3-2 위반이다.

4. **"필요한 포트만 허용"(R3-1)과 "전체 포트 허용 규칙 금지"(R3-4)는 강도가 다른 별개 조항이다.** R3-1은 원칙이고 R3-4는 **절대 금지선**이다. 디버깅 중에 잠깐 전체를 열었다가 스크린샷에 그 규칙이 찍히면 그대로 위반 증거가 된다.

5. **`AdministratorAccess` 미부여(R4-3)와 "실습과 무관한 서비스 권한 미부여"(R4-2)는 다른 조건이다.** Admin을 피했더라도 `AmazonS3FullAccess` 를 붙여두면 R4-2 위반이다. 반대로 권한을 너무 조이면 실습 자체가 막히므로, **실패 → CloudTrail/오류 메시지로 필요한 액션 특정 → 그 액션만 추가**의 반복이 이 요구사항이 기대하는 작업 방식이다.

6. **`docs/` 경로와 파일명이 고정 규격이다.** `docs/architecture.(png|pdf)`, `docs/troubleshooting.(md|pdf)`, `docs/cleanup-checklist.md`. 내용이 아무리 좋아도 위치·이름이 다르면 "제출 최소 규격" 미충족으로 읽힐 수 있다.

7. **"선택한 방식(A/B)은 `README.md` 에 명시한다"(R5-2)는 스크린샷과 별개의 요구다.** 스크린샷만 붙이고 A인지 B인지 문장으로 안 쓰면 미충족이다. 접속 정보(URL 또는 IP)도 함께 적어야 한다.

8. **트러블슈팅 보고서는 6단계를 *모두* 요구한다.** 특히 마지막 **재발방지**가 빠지기 쉽다. 또 "최소 1건 이상"이므로 실제로 겪은 고장이 없다면 **의도적으로 고장을 만들어 재현**해야 한다 (예: SG에서 80을 지우고 접속 실패 → 복구).

9. **정리 대상 목록이 두 군데에 있고 범위가 다르다.** R6-2는 **최소 5종**(EC2, EBS, Elastic IP, Internet Gateway, VPC)이고, 제약 사항 "운영/정리(필수)"는 여기에 **NAT Gateway, ELB/ALB, RDS**(생성했다면)를 더한다. 특히 **연결되지 않은 Elastic IP는 유휴 상태에서 오히려 과금**되므로 Release를 잊으면 안 된다.

10. **리전은 `ap-northeast-2` 고정이다.** 콘솔이 기본으로 다른 리전을 띄워둔 상태에서 리소스를 만들면 제약 위반이자, 정리할 때 "분명 다 지웠는데 청구가 남는" 전형적 사고의 원인이 된다.

| `SSH_CIDR` `case` 에 기본 분기 `*)` 추가 | IPv6 같은 비 IPv4 값이 통과해 두 단계 뒤에서 엉뚱한 메시지로 나타나던 경로(위 격차 8)를 값이 만들어진 자리에서 끊었다 | `infra/02_security_group.sh` |
| `99_cleanup.sh` 인자 처리를 `case` + `*)` 로 | `--Yes`, `-y` 같은 오타가 조용히 무시된 채 실행되던 것을 거부한다 | `infra/99_cleanup.sh` |
| 서브넷 연결 검사 ID 를 `B6-1-N6` 로 분리 | 별개 실패 지점이 같은 ID 를 쓰면 로그만 보고 구분할 수 없다 | `infra/04_verify.sh` |
| `set -eux` → `set -euxo pipefail` | 파이프 중간 실패를 삼키지 않는다 | `infra/user-data.sh` |
| `pyproject.toml` 추가 | 실행 규격(파이썬 버전, 테스트 실행기)을 문서가 아니라 파일로 선언한다. 런타임 의존성은 0 이다 | 루트 |
| 테스트 45 → 55개 | 위 규칙들을 **실행되는 검사**로 옮겼다. 합계 등식, 계약 위반 시 정지, `case` 기본 분기, 안전 옵션, 판정 출력 단일화 — 다섯 가지 모두 한 번씩 일부러 깨뜨려 빨간 불을 확인한 뒤 되돌렸다 | `tests/test_infra.py`, `tests/fake_aws.py` |

이 표의 판정 근거를 `파일:줄번호` 대신 **검사 ID·함수 이름·절 이름**으로 적은 것도 같은 이유다.
줄번호는 리팩터링에 견디지 못하는 좌표라, 코드를 한 줄만 옮겨도 근거가 거짓이 된다.
0.10 표에서 위 파일들을 가리키던 줄번호 참조도 전부 안정적 좌표로 바꿨다.

## 1. 아키텍처

![아키텍처 다이어그램](docs/architecture.png)

원본 파일: [`docs/architecture.png`](docs/architecture.png) / 벡터 편집용 [`docs/architecture.svg`](docs/architecture.svg)
(둘 다 [`docs/build_architecture.py`](docs/build_architecture.py) 가 같은 좌표에서 생성한다)

### 외부 요청이 EC2 까지 도달하는 경로

```text
브라우저  →  Internet Gateway  →  Public Subnet  →  Security Group  →  EC2 (nginx :80)
             ①                    ②                 ③                  ④
```

| 단계 | 없으면 어떻게 되나 | 이 저장소에서 담당하는 곳 |
| --- | --- | --- |
| ① IGW 가 VPC 에 **연결**돼 있어야 한다 | VPC 는 인터넷과 물리적으로 이어지지 않는다 | `01_network.sh` |
| ② Route Table 에 `0.0.0.0/0 → IGW` 가 있어야 한다 | 패킷이 IGW 로 갈 길을 모른다. **연결만으로는 부족하다** | `01_network.sh` |
| ③ Security Group 인바운드에 80 이 열려야 한다 | 서브넷까지 온 패킷이 인스턴스 앞에서 버려진다 | `02_security_group.sh` |
| ④ 인스턴스에 **퍼블릭 IP** 가 있고 nginx 가 살아 있어야 한다 | 바깥에서 부를 주소가 없거나, 주소는 있는데 응답이 없다 | `03_instance.sh` + `user-data.sh` |

②가 핵심이다. **Public Subnet 을 "퍼블릭"으로 만드는 것은 이름이 아니라 라우팅**이다.
서브넷 이름을 `public` 으로 지어도 기본 경로가 없으면 사설 서브넷이다.

## 2. 실행 순서

### 사전 준비

1. AWS 계정에 **IAM 사용자**를 만들고 [`iam/codyssey-b6-1-policy.json`](iam/codyssey-b6-1-policy.json) 을 연결한다
   → 방법은 [`iam/README.md`](iam/README.md)
2. 그 사용자의 액세스 키로 `aws configure` (루트 계정 키는 쓰지 않는다)
3. `aws --version` 과 `aws sts get-caller-identity` 로 확인

### 구축

```bash
bash infra/01_network.sh          # VPC / Subnet / IGW / Route Table
bash infra/02_security_group.sh   # 보안 그룹 (내 IP 자동 감지)
bash infra/03_instance.sh         # 키페어 / AMI 조회 / EC2 기동 + nginx
bash infra/04_verify.sh           # 요구사항 자동 검증
```

각 스크립트는 만든 리소스 ID 를 `infra/.state` 에 적는다. **다시 실행해도 새로 만들지 않고
기존 것을 재사용**한다.

여기서 한 가지를 구분한다. 리소스 **생성**은 ID 가 있으면 건너뛰지만,
생성에 딸린 **부속 작업**(DNS 속성, 퍼블릭 IP 자동할당, IGW 연결, 기본 경로, 서브넷 연결)은
건너뛰지 않고 **매번 현재 상태를 조회해 없으면 채운다.** 그래서 1회차가 부속 작업 도중에 죽어도
고친 뒤 그대로 다시 돌리면 누락분이 복구된다. (이걸 안 하면 ID 만 남은 채 재실행이 "재사용"으로
통과해 기본 경로가 영영 생기지 않는다 — 증상은 "인스턴스는 running 인데 브라우저에서 안 열림"이다.)

### 검증

```bash
bash infra/04_verify.sh | tee docs/verification.txt
```

요구사항 ID 마다 PASS / FAIL 을 찍는다. "된다고 썼다"가 아니라 "확인했다"를 남기기 위한 것이다.

```text
── 네트워크 구성 ─────────────────────────────────────────────
[PASS] B6-1-N1      VPC 1개 존재
       B6-1-N1      VPC CIDR: 10.0.0.0/16
[PASS] B6-1-N4      Route Table 에 0.0.0.0/0 → IGW 경로 존재
       B6-1-N4      기본 경로: 0.0.0.0/0 → igw-0abc...
...
```

### 정리 (반드시)

```bash
bash infra/99_cleanup.sh
```

의존 관계의 역순으로 지우고, 태그로 다시 훑어 잔여 리소스가 없는지 확인한다.
자세한 항목은 [`docs/cleanup-checklist.md`](docs/cleanup-checklist.md).

## 3. 외부 접속 검증

**선택한 방식: (B) 헬스체크 — `GET http://<퍼블릭IP>/health`**

과제는 (A) 브라우저 접속과 (B) 헬스체크 중 하나를 고르게 한다. (B) 를 택한 이유는
**결과가 눈이 아니라 값으로 남기 때문**이다. 상태 코드와 고정 응답 문자열은 스크립트가
자동으로 비교할 수 있어, `04_verify.sh` 가 매번 같은 기준으로 판정한다.
(A) 도 함께 확인하며, `04_verify.sh` 는 둘 다 검사한다.

| 항목 | 값 |
| --- | --- |
| 퍼블릭 IP | `<배포 후 채우기 — infra/.state 의 PUBLIC_IP>` |
| 접속 URL (A) | `http://<퍼블릭IP>/` |
| 헬스체크 URL (B) | `http://<퍼블릭IP>/health` |
| 기대 응답 | `200 OK` / 본문 `OK` |

```bash
$ curl -i http://<퍼블릭IP>/health
HTTP/1.1 200 OK
Server: nginx
Content-Type: text/plain

OK
```

스크린샷은 [`docs/screenshots/`](docs/screenshots/) 에 넣는다 (넣을 목록은 그 폴더의 README 참고).

## 4. 보안 — 무엇을 열고 무엇을 닫았나

| 방향 | 포트 | 소스 | 이유 |
| --- | --- | --- | --- |
| 인바운드 | tcp 80 | `0.0.0.0/0` | 웹 서비스는 누구나 들어와야 한다 |
| 인바운드 | tcp 22 | `<내 IP>/32` | 관리 포트. **나만** |
| 인바운드 | 그 외 | — | 없음 |
| 아웃바운드 | 전체 | — | 기본값. 패키지 설치와 업데이트에 필요하다 |

`0.0.0.0/0` 에 대한 **전체 포트(0-65535) 허용 규칙은 만들지 않는다**(과제 금지 사항).
이건 주의로 지키지 않고 **코드로 막는다**:

- `02_security_group.sh` 는 `SSH_CIDR=0.0.0.0/0` 을 받으면 **실행을 거부**한다
- 규칙을 넣은 직후 [`infra/check_sg.py`](infra/check_sg.py) 가 스스로 점검하고, 어기면 종료 코드 1
- `04_verify.sh` 가 같은 검사를 다시 한다 (판정 로직은 한 파일에만 있어 둘이 어긋나지 않는다)

### SSH 를 굳이 좁히는 이유

22 번을 전체 공개하면 몇 분 안에 자동화된 로그인 시도가 들어온다.
키 인증만 허용해도 로그는 지저분해지고, 언젠가 설정 하나가 어긋나면 그게 문이 된다.
**"임시로 열고 잊는" 것이 사고의 전형적인 모양**이라, 애초에 만들 수 없게 했다.

내 IP 가 바뀌어 접속이 안 되면 → [`docs/troubleshooting.md`](docs/troubleshooting.md) 사례 2.

## 5. 권한 — 최소권한 원칙

[`iam/codyssey-b6-1-policy.json`](iam/codyssey-b6-1-policy.json) 하나만 붙인다.

- `AdministratorAccess` **미부여** — `04_verify.sh` 가 매번 확인한다
- `s3:*`, `rds:*` 등 실습과 무관한 서비스 권한 **없음**
- `iam:CreateUser`, `iam:AttachUserPolicy` 같은 **권한 상승 경로 없음**
- 대부분의 Statement 에 `aws:RequestedRegion = ap-northeast-2` 조건 → 다른 리전 생성 자체가 거부된다

### Security Group 과 IAM 은 무엇이 다른가

| | Security Group | IAM |
| --- | --- | --- |
| 대상 | **패킷** — 인스턴스에 도달하는 트래픽 | **API 호출** — AWS 를 조작하는 요청 |
| 질문 | "이 주소에서 이 포트로 들어와도 되나" | "이 사용자가 이 리소스에 이 작업을 해도 되나" |
| 어겼을 때 | 연결이 끊기거나 타임아웃 | `AccessDenied` / `UnauthorizedOperation` |
| 이 실습의 예 | 80 은 공개, 22 는 내 IP | EC2 는 만들 수 있지만 S3 는 못 본다 |

둘은 **서로를 대신하지 못한다.** SG 를 아무리 좁혀도 IAM 이 열려 있으면
콘솔에서 규칙을 바꿔 버릴 수 있고, 반대로 IAM 이 좁아도 SG 가 열려 있으면 트래픽은 들어온다.

권한이 모자라 실패하면 → 정책을 넓히지 말고 오류 메시지의 액션 하나만 추가한다.
방법은 [`iam/README.md`](iam/README.md) 마지막 절.

## 6. 과금 방지

| 장치 | 어디에 |
| --- | --- |
| 생성 시점부터 `Project=codyssey-b6-1` 태그로 **추적** | 모든 `create-*` 호출 |
| 루트 EBS `DeleteOnTermination=true` — 고아 볼륨이 안 남는다 | `03_instance.sh` |
| NAT Gateway / ELB / RDS 를 **만들지 않고**, IAM 정책에도 권한이 없다 | `iam/codyssey-b6-1-policy.json` |
| 정리 후 태그로 다시 훑어 잔여 확인, 남으면 실패 처리 | `99_cleanup.sh` |
| 리전 조건으로 타 리전 생성 차단 | IAM 정책 |

프리 티어 범위: t3.micro 1대 + EBS 8GiB. **EIP 는 할당하지 않는다** —
연결되지 않은 EIP 는 시간당 과금되는데, 인스턴스를 지우는 순간 정확히 그 상태가 되기 때문이다.

| 검사하는 것 | 예 |
| --- | --- |
| 명령 구성 | `create-route` 가 `0.0.0.0/0 → igw-...` 인가 |
| 금지 규칙 | 전체 포트 허용을 만들지 않는가, `SSH_CIDR=0.0.0.0/0` 을 거부하는가 |
| 리전 고정 | **모든** 호출에 `--region ap-northeast-2` 가 붙는가 |
| 과금 안전장치 | `DeleteOnTermination=true` 인가, 추적 태그를 다는가 |
| 삭제 순서 | terminate → SG → route table → IGW → subnet → VPC 순인가 |
| 잔여 확인 | EC2 / EBS / EIP / IGW / VPC 5종을 모두 조회하는가 |
| 재실행 안전성 | 두 번째 실행이 리소스를 새로 만들지 않는가 |
| **부분 실패 복구** | 기본 경로 생성이 실패한 뒤 재실행하면 그 경로를 채우는가 |
| 키 파일 권한 | `.pem` 이 `0400` 인가 |
| **검증 스크립트 자체** | `04_verify.sh` 의 합계(`PASS n / FAIL m / SKIP k`)가 **실제로 찍힌 판정 줄 수**와 같은가 |
| **파일 간 계약** | `check_sg.py` 가 집계를 안 남기면 `04_verify.sh` 가 **멈추는가** (조용히 0 으로 세지 않는가) |
| **조용한 실패** | 모든 `case` 문에 기본 분기 `*)` 가 있는가, 모든 셸 스크립트가 `set -euo pipefail` 아래 도는가 |
| 판정 출력 | `[PASS]/[FAIL]/[SKIP]` 형식이 `pass()`/`fail()`/`skip()` **한 곳씩**에만 있는가 |
| 의존성 0 | `infra/*.py` · `tests/*.py` 가 표준 라이브러리 밖의 모듈을 import 하지 않는가 |

`04_verify.sh` 는 `aws` 와 `curl` 을 **둘 다** PATH 앞에서 가로챈 채로 실행된다.
그래서 판정 로직은 실제로 돌지만 네트워크로는 한 바이트도 나가지 않는다.

**이 테스트가 확인하지 못하는 것**: 실제 AWS 의 응답, 권한, 과금, 네트워크 도달성.
그건 계정에서 `bash infra/04_verify.sh` 로만 확인된다. 두 층을 섞어 말하지 않기 위해
테스트 파일 첫머리에도 같은 한계를 적어 두었다.
